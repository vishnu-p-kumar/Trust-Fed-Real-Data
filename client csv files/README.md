# Client CSV test samples

Use these files in the client portal with the default feature columns and `is_theft` label. Open a fresh round for each upload; a client can submit once per round.

- `2. correct csv file/correct_smart_meter.csv`: 1,000 labeled rows; expected to pass coordinator validation.
- `1. poisoned csv file/poisoned_smart_meter_no_marker.csv`: 600 rows selected from the label-flipped clients; the `is_poisoned` marker and client identifiers have been removed. Expected to fail coordinator validation and lower that client?s trust score.

Both samples are synthetic/demo data derived from the two CSVs supplied for this task. A pass/fail result demonstrates this project?s current demo validation, not a guarantee against every poisoning strategy.

## Client upload set

- `clenet.csv` combines 1,000 clean rows and 600 marked poisoned rows. It is a single mixed demonstration file; because it contains `is_poisoned=1` rows, the client portal should reject its update.
- `clear data/clear_data.csv` contains the clean rows with `is_poisoned=0` and is suitable for a clean client upload.
- `poisoned data/poisoned_data.csv` contains the poisoned rows with `is_poisoned=1` so the portal can identify and reject the marked update.

All three files retain the portal's default features (`voltage`, `current`, `power`, `consumption_kwh`, `power_factor`) and `is_theft` label. These are synthetic client examples, not utility data.

For this five-feature client demo, the coordinator evaluates updates against a fixed, coordinator-owned labeled reference generated by the project's meter simulator. It does not use the uploaded client CSV as its validation set. Marked poisoned rows are rejected from the submitted `is_poisoned` count; the unmarked poisoned sample is assessed by coordinator validation.
